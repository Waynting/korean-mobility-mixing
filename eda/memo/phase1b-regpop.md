# Phase 1b — 登記人口到手，洞界對照表建完

*2026-08-17。腳本 `eda/dl_regpop.py`（拉檔＋逐檔驗證）、`eda/p20_regpop.py`（對照表＋攝入）。
產出 `derived/regpop.parquet`（1,076,605 列）、`derived/dong_crosswalk.parquet`（424 列）、
`eda/results_p20.json`。原始檔 79 份 cp949 CSV 在 `$KOREAN_DATA_ROOT/raw/regpop/`，
`manifest.json` 存每份的 sha256、列數、全國總計。*

計畫給 Phase 1b 排的是 5–6 天、標成「這是長桿」。**結果比預期乾淨很多**，
主要因為擋在前面的兩個未知（洞界改編多不多、兩套碼對不對得起來）答案都是「幾乎不改」。

## 1. ✅ 拉檔：79 個月全到，逐檔驗證通過

`jumin.mois.go.kr` 沒有 API，但 통계표 頁的隱藏表單直接 POST 到 `downloadCsvAge.do`，
改三個參數就得到要的東西：`sltArgTypes=1`（單歲，預設是 10 歲距）、`xlsStats=3` 與
`state=3`（전체읍면동현황，預設只給當前畫面）。一個月一次請求，2020-01 → 2026-07 共 79 次。

**驗證不是看 HTTP 狀態碼。** 韓國政府入口網回一頁 session timeout 的 HTML 時，
一樣是 200、一樣帶 `Content-Disposition`。所以每份檔在落地當下要通過：cp949 可解、
310 欄、欄名帶著**請求的那個年月**、≥3,000 列、시도 列加總落在全國人口的合理區間、
每一列 `계 = 남 + 여`、`총인구수 = 101 個單歲欄之和`。任何一項不過就重試，三次不過就報錯。

這組檢查抓到一件真事：**2026-07 只有 16 個 시도，不是 17。**
`광주광역시` 與 `전라남도` 併成 `전남광주통합특별시`（碼 1200000000）。
檔案是對的，寫死的 17 才是錯的。不影響首爾，但它證明逐檔驗證在做事——
這一項若沒設，2026-07 會安靜地少一個 시도 進來。

## 2. ✅ 碼對照：424 個產品洞對登記洞，1:1 全中

兩套碼依建構就對不起來：생활이동 用自有 7 碼制（`11` + 2 碼區序 + 3 碼洞序），
登記檔用 MOIS 10 碼 행정기관코드。所以只能用**（區名, 洞名）**join，而兩邊的正寫法不同：

| | 生活移動 | 登記檔 |
|---|---|---|
| 序數 | `상일1동` | `상일제1동` |
| 分隔 | `종로1·2·3·4가동` | `종로1.2.3.4가동` |

**規範化要分兩邊做，不能兩邊套同一條規則。** 只有登記側把序數寫成 `제N동`，
而 `홍제1동` 的 `제` 是名字的一部分不是序數——兩邊都套一次剝除，`홍제1동` 會被弄成 `홍1동`，
而且它會安靜地變成 3 個假的不匹配。做法是：`.` → `·` 兩邊都做；剝 `제` 只對登記側做，
而且用 `제(\d[\d·]*동)$` 錨在字尾。

結果：**產品 424 個首爾洞全部對上，一個不漏。**
（另外順帶確認：官方코드표共 1,152 列，與 `results_p16.json` 實測的碼空間 1,152 一致。）

## 3. ⚠️ 2020-01 登記檔有 425 個洞，產品只有 424 —— 差的是 구로구 항동

**항동（MOIS 1153080000）在 79 個月裡每個月都在登記檔，從來不在생활이동的碼空間裡。**
2020-01 人口 13,365 人，佔首爾 0.137%；全窗 1,272,613 人月，佔 0.170%。

年齡結構看得出是新開發區（0–9 歲 2,218 人，是 65+ 全部 1,157 人的兩倍）。

**這件事對 $\hat\rho$ 的後果要講清楚。** 항동 的居民有兩種可能：
(a) KT 把他們算進鄰洞（최可能是 수궁동，항동 的碼 080 緊接 수궁동 079），
(b) 產品根本沒有他們。**兩者對分母的處置相反**，而且可以用資料判：
分別在「수궁동分母含항동」與「不含항동」兩種設定下算 구로구 各洞的 $\hat\rho$，
看哪一種讓 수궁동 落回區內其他洞的分布裡。若錯配，수궁동 的分母會差
13,365 / 24,483 = **55%**，大到一定看得出來。**這是 Phase 1c 的一個具名檢定，不是註腳。**

> ✅ **2026-08-17 結案：오류2동。** 檢定做在 `p21_rho.py` §1.6（구로구 15 個洞全部當候選，
> 不只碼相鄰的那兩個）：只有 오류2동 讓全區的 $\hat\rho$ 離散度下降（RMS 0.1192 → 0.0977），
> 其餘每一個都讓它變糟；오류2동 本來就是全區唯一的 +2σ 離群值，加上 항동 之後回到 +0.39σ。
> 我從碼相鄰猜的 수궁동 **被資料推翻**——它的 $\hat\rho$ 恰好是區中位數，加進 항동 反而推到 −1.5σ。
>
> **後來取得的第二個獨立訊號指向同一個洞。** `p20c_covariates.py` 把통계청 SGIS 的 행정동 邊界
> 對上產品碼空間時發現：**424 個產品洞裡有 423 個的 `adm_cd` 與產品碼完全相同，唯一的例外是 오류2동**
> （통계청 1117073 對產品 1117068），而통계청的碼空間裡**多出來的那一個正是 항동**（1117074）。
> 也就是說：碼空間唯一挪動過的洞，正是 $\hat\rho$ 檢定指認的那一個。
> ⚠️ 這是**旁證不是證明**——「碼挪動是因為 항동 從它切出去」是推論，不是文件記載的事實。

## 4. ✅ 洞界改編：六年半只有三件，而且只有兩件要錢

| 月份 | 類型 | 內容 |
|---|---|---|
| 2021-07 | **split** | 강동구 상일동（38,683 人）→ 상일1동 + 상일2동 |
| 2022-12 | rename | 강남구 일원2동（17,358 人）→ 개포3동 |
| 2025-07 | **split** | 동대문구 용신동（38,829 人）→ 신설동 + 용두동 |

rename 免費（同一塊地換標籤）。兩個 split 要錢：跨事件沒有任何單一洞可比，
兩側都得併成一個縱向單位。

**Stable units：430 個曾出現過的洞名收成 425 個單位，只有 3 個單位包住不只一個名字，
涵蓋 8 個名字＝1.9%。**

> 計畫的反證門檻是：**若超過 ~10% 的洞被併進合併後的 stable units，
> 論文框架裡「鄰里尺度」的宣稱就變弱。** 實測 **1.9%**，門檻沒被碰到。
> 鄰里尺度的宣稱站得住，Phase 5（解析度）的緊迫性維持原判、沒有提前。

三個 split/rename 的母洞（상일동、일원2동、용신동）**都在產品的 424 裡**，
所以經 stable unit 併回之後，**產品覆蓋首爾除 항동以外的全部**。

⚠️ 一個必須在 Phase 2 查的連帶問題：官方코드표日期是 **2021-09-07**，
在 2021-07 的 상일동 split **之後**，而它列的仍然是 `상일동`，不是 상일1/2동。
這暗示**產品維持自己凍結的碼空間、不跟著行政區改編走**——若成立，2020–2026 的產品
碼空間會一直是 424，縱向可比性反而更好。但這是從一份文件推的，
**要用 2021+ 的實際 parquet 碼集合驗證**（Phase 2a schema 稽核順手做掉）。

## 5. ✅ 質量守恆：79 個月逐月精確
