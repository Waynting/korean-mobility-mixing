# Phase 36 — 招牌數字的獨立第二實作

腳本 `eda/p36_recompute.py` → `results_p36.json`。

## 為什麼要有

老師 8/19 的結尾：一輪裡出現三次「水準錯掉、比值卻合理」，而答案不是更大的閘門。
`p31` 檢查的是「報告有沒有正確引用 `results_*.json`」，它**沒辦法**檢查
`results_*.json` 本身對不對，因為它讀的是同一個檔。所以招牌數字在這裡用另一條路
再算一次。

## 「獨立」在這裡的確切意思

| | 原路徑 | `p36` |
|---|---|---|

| 到達快取 | 讀 `derived/arrivals_dow_*.parquet` | **不讀**，每次回到 parquet |
| 日曆 | `calendar_kr.py`（人工輸入的假日表） | **`holidays` 套件 + `calendar` 模組**重新導出 |
| 調查矩陣 | pandas merge + `np.add.at`（`p27`） | **`csv` 模組 + dict + 迴圈** |
| assortativity | numpy | 純 Python 依定義展開迴圈 |
| 主特徵值 | `numpy.linalg.eig` | **冪次迭代** |
| 奇異值 | `numpy.linalg.svd`（`p32`） | **冪次迭代 + 收縮**，$M=e'e$ 先除以自己的跡 |
| 學期標籤 | `p41` 的 `TERM`/`VAC` 常數 + `p42` 存下的 `semester` 欄（`p58`） | **從 ym 自己導**，兩個學期集合就地重述 |

ETL 已經逐檔對過來源 CSV 的 `wc -l`（`etl_report.json`），那比第二實作更強。

## 逐位元可重現性：這支腳本自己第一版不可重現，原因值得記下來

老師 8/19 的教訓是「一支會漂的腳本不能拿去發表」（`p34` 的 `hash()` 隨機化）。所以本輪把
`p33`／`p35`／`p36` 各跑兩次逐位元比對。前兩支一次就過，**`p36` 沒過**：

| | 兩次跑的結果 |
|---|---|
| `p33_coverage`（`--boot 400`） | **逐位元相同**（28,769 bytes，sha256 `11b98f96fc337ece`） |
| `p35_seir`（`--boot 200`） | **逐位元相同**（27,832 bytes，sha256 `22786cb579b53845`） |
| `p32_pmix` | **逐位元相同**（125,419 bytes，sha256 `dac1d1ea8e03a908`） |
| `p36_recompute`（第一版，threads=6） | **82 項有 21 項不同**，相對差 ~1e-15；兩次都 82/82 通過 |
| `p36_recompute`（修正後，threads=1） | **逐位元相同**（11,476 bytes，sha256 `23d53eb53ab274e5`） |

**原因不是 bug，是 DuckDB 的平行雜湊聚合。** 多執行緒把部分和依執行緒完成順序合併，而浮點
加法不可結合。把 18M 列的自連接抽出來單獨測：

| | 同一個查詢連跑三次 |
|---|---|
| `threads=6` | **不相同**（第一個差異在 (0–9, 0–9)：1028435.9421344618 對 …615，相對 3.4e-16） |
| `threads=1` | **完全相同** |

而單純的 `sum(pop) GROUP BY age` 在 threads=6 下是穩定的——分組夠大、每組列數夠少時碰不到；
要 18M 列的聚合才看得見。

**處置：`p36` 改成 `PRAGMA threads=1`（`--threads` 可覆蓋）。** 成本量過了：
`passive_matrix` 從 1.2 秒變 5.3 秒，八個矩陣多約 40 秒。任何結論都不在 1e-15 上，82 項在
兩種設定下都以 1e-6 的容差通過並有很大餘裕——但**一支專門用來當「可重現的第二意見」的腳本，
自己不能不可重現。**

⚠️ **連帶的一件事要記下來但不必處理：`p26` 的 `arrivals_dow_*.parquet` 快取也是多執行緒
DuckDB 聚合產生的**，所以 `results_p26.json` 帶的是那個抖動的某一個實現值。刪掉快取重跑
`p26`，已發表的 assortativity 可能在第十五位數字上動。知道就好。

檢查本身也做成可重跑的：`eda/determinism_check.sh p33_coverage p35_seir p36_recompute`，
把腳本跑兩次、比 sha256，不相同就印出前幾個差異鍵。「我跑了兩次比對過」在變成一個誰都能跑的
指令之前，只是信裡的一句話。

⚠️ **跑檢查的時候不要 commit。** 它在兩次執行之間會刪掉 `results_pNN.json`，那個視窗裡取的
commit 會記錄一個被刪掉的結果檔——8/19 當晚就這樣掉過一次，只好從 git 復原。第一版把備份放在
`$TMPDIR` 裡而那個目錄結束時會被 `rm -rf`，所以被中斷的執行等於備份也一起沒了；現在備份寫在
結果檔旁邊（`results_pNN.json.determinism-backup`，已 gitignore），中斷之後一個 `mv` 就救回來。

上面那張表量的是 8-19 當晚的版本，而那兩支腳本後來都長大了：`p35` 在 `c9fa917` 加了退階那一節，

|---|---|---|

證據。加上 `p32`、`p33`、`p34`，五支腳本的**現行版本**都有這一格。

⚠️ **跑檢查的時候不要改 `determinism_check.sh` 自己。** 這次 p36 跑到一半（20:56 起跑，21:06 有人
改了那個檔的一段註解），zsh 是按位元組位移邊讀邊執行腳本的，檔案在腳下換掉之後位移就對不上，
結果是它把該做的事全做完、把 `All checked scripts are byte-reproducible.` 印出來之後，
在 EOF 報了一個 `:126: unmatched "` 並以 exit 1 收場。**那個 1 不是重現性失敗**，
但任何看 exit code 的自動化都會把它讀成失敗。與「不要在這個窗口 commit」同一類的規矩：
檢查在跑的時候，它自己與它要跑的腳本都不要動。

真正被 assert 的是那句結論：**三種數法下都恰好一個讀數 ≥ 0.95，而且是同一個**——
`p44` §44.1–44.2 點名並否決的 with-replacement 配對 0.96155。結論不隨規則變，
這比「數字對上了」有用。

**36.12 的機制檢查是這一節裡唯一回答「它不是 bug」的東西。** 合併讓 r 上升是反直覺的，所以要問：
這個算子會不會從一個本來沒有 assortativity 的矩陣裡造出 assortativity？把 $e_{ab}=r_a r_b$ 的
比例混合矩陣**自己建一遍**（直接從原始列和形成 $R_iR_j/R_\cdot$，不走 `p60` 先正規化再放大那一步），
79 個月 × 5 個階級收下來，最大 $|r|$ = **4.484e-16**（`p60` 量到 4.940e-16）。兩邊都是數值零而不是
同一個數，所以這一格記成「兩者皆為零」的判定，不是逐位錨——把兩個相減抵消的浮點結果拿去對位元
沒有意義。

## 36.3c：唯一一格不是錨的檢查，照 §45.4 的規矩報

`p61` 的置換虛無不能當錨，也不該被裝成錨。換一條隨機串流畫 500 次置換，中位數不可能逐位重現；
沿用 `p61` 的種子（20260827）只會證明同一次抽樣的兩份副本一致。所以 36.3c 用**自己的種子與自己
的產生器**（`random.Random`，不是 numpy），而且：

- 中位數與 p95 只在**蒙地卡羅誤差內**比對，容差是先把算術宣告出來的：`p61` 報 sd 0.0178／500 抽，
  中位數的標準誤約 `1.25·sd/√500 = 0.0010`，即 0.8%；兩次獨立跑差 √2 倍，5% 是寬鬆的三個標準差；
  p95 動得比中位數大，所以給 10%。
- 真正被 assert 的是**判定**：觀測值有沒有逃出自己的虛無。那是論文讀的東西，也是不隨串流變的
  東西。

量到的：202312 中位數差 **0.23%**、p95 差 **1.98%**；202402 差 **0.40%**／**1.63%**；
四個判定（兩個月 × σ₂/σ₁ 與 σ₁-share）**全部與 `p61` 一致**。`p61` 自己的 `replay_at_p32_seed`
也是同一件事的另一個實例，兩邊的量級一致。

## 最差相對差從 9.5e-15 變成 1.52e-13，而原因是相減抵消，不是漂移

新的最差一格是 `p59 spread of the four declared rules`：四個 β\* 各自逐位相符（相對差 ~1e-16），
但它們的**跨度**只有 7.3e-4，於是 2e-16 的絕對誤差被放大成 2.7e-13 的相對誤差。
`p31` 的「exact 子集最差 < 1e-12」仍然過，餘裕約六倍。**凡是報「差值」的量都會這樣**，
寫在這裡免得下次有人把它讀成漂移。

## 侷限

- `p33`/`p35` 沒有進來，它們各自帶硬錨（`p33` 對 `p26` 逐位、`p35` 對有限差分、RK4 與
  退階的四個 anchors）。
- 36.9 把掃描的中位數當成給定值；能查的是它的兩個確定性端點與所有下游算術。
- 36.10 的 79 個 `mi_bits_hf` 與 36.12 的 79 個矩陣沒有重建（理由與代價在上面那一節）；
  36.11 讀的是 `p59` 存下的 `q_lo_corr` 曲面，蒙地卡羅那一半（100 次重複 × 11 個 r_true
  × 5 個 β）不重跑，被重算的是曲面之上的每一步。
- 36.3c 是唯一一格不是錨的檢查；它 assert 的是判定，中位數只在蒙地卡羅誤差內比對。
- 共用而未被檢查的仍然是 DuckDB 的 parquet reader 與 ETL 本身。
